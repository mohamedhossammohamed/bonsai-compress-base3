Ternary weights, packed in base 3, decoded in registers — 1.6 bits each, zero loss, faster every token.

Five trits fit in one byte (3⁵=243≤256). The repack shrinks ternary weights from 2.00 → 1.60 bits each — bit-exact by arithmetic identity, no retraining, no calibration. Fewer bytes per token should mean proportionally faster bandwidth-bound decoding; the fused engine around it is built to compound that. Theory and verification roadmap below — predictions graduate to logged results as the protocol runs.

Scheme S2 in one picture

Pack16 trits × 5 words → 80 trits → 16 bytes. 2.00 → 1.60 b/w, streaming, <500MB RAM.
StreamOut-of-core mmap streamer pages tiles on demand; paged KV, 10.5GB guard on 16GB Macs.
DecodeBase-3 unpack + scale fused into GEMV in registers/Metal. 0.4566 → 0.3614 ms/layer.

Because 243 of 256 byte values are valid trit-quintuples, any byte decodes to exactly 5 trits — the mapping is an arithmetic identity, so reconstruction error is zero by construction, not by benchmark. Full proofs: THEORY_S2.md.

Two mechanisms, one page. The repack (lossless math) and the fused decode engine (predicted speedups) are independent — either works without the other. Model quality lives in the upstream ternary checkpoint, which you supply and evaluate.

Serving architecture

64-layer hybrid (48 Gated-DeltaNet linear attention + 16 full GQA with FWHT), BonsaiWeightStreamer out-of-core paging, NGramDrafter speculative decoding, Metal layer kernels and a C dequant core — all in runtime/, with an OpenAI-style server (bonsai_server.py).

The key file is runtime/metal_base3.py: Metal kernels that unpack base-3 bytes to trits and run fused GEMV inside the same kernel — weights are never decompressed to memory, only to registers on the way into the dot product. Base3Linear wraps this as a drop-in MLX layer; tests/test_base3_equivalence.py checks bit-exactness.
